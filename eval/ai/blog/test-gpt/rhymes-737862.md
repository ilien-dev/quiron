# How to wrap a Preact component into a Stimulus controller

Stimulus and Preact solve different problems, which makes them surprisingly good companions.

Stimulus adds behavior to existing HTML. Preact renders component trees and manages their state. By wrapping a Preact component in a Stimulus controller, you can introduce rich, component-based interfaces without turning your entire application into a single-page app.

This pattern is especially useful in server-rendered applications such as Rails, Laravel, Django, or Phoenix. The server remains responsible for pages and data, Stimulus discovers interactive regions, and Preact handles only the UI that genuinely benefits from component state.

## Install the dependencies

Start by installing Stimulus and Preact:

```bash
npm install @hotwired/stimulus preact
```

This article assumes that your build system supports JSX. Vite supports Preact through `@preact/preset-vite`, while other bundlers may require their JSX import source to be configured as `preact`.

A minimal Stimulus application might look like this:

```js
// application.js
import { Application } from "@hotwired/stimulus"
import PreactWidgetController from "./controllers/preact_widget_controller"

window.Stimulus = Application.start()
Stimulus.register("preact-widget", PreactWidgetController)
```

If your framework already initializes Stimulus automatically, you only need to add the controller file in its expected location.

## Create the Preact component

Suppose we want a small counter that greets the current user:

```jsx
// components/Counter.jsx
import { useState } from "preact/hooks"

export function Counter({ name, initialCount = 0, onCountChange }) {
  const [count, setCount] = useState(initialCount)

  function increment() {
    const nextCount = count + 1
    setCount(nextCount)
    onCountChange?.(nextCount)
  }

  return (
    <section class="counter">
      <p>
        Hello, {name}. The current count is {count}.
      </p>

      <button type="button" onClick={increment}>
        Increment
      </button>
    </section>
  )
}
```

There is nothing Stimulus-specific in this component. It receives props, owns local state, and reports changes through a callback. Keeping the component independent makes it easier to test and reuse.

## Build the wrapper controller

The controller’s job is to translate the DOM-oriented Stimulus lifecycle into Preact render operations:

```jsx
// controllers/preact_widget_controller.jsx
import { Controller } from "@hotwired/stimulus"
import { render } from "preact"
import { Counter } from "../components/Counter"

export default class extends Controller {
  static values = {
    name: String,
    initialCount: {
      type: Number,
      default: 0,
    },
  }

  connect() {
    this.connected = true
    this.renderComponent()
  }

  disconnect() {
    this.connected = false
    render(null, this.element)
  }

  nameValueChanged() {
    this.renderIfConnected()
  }

  initialCountValueChanged() {
    this.renderIfConnected()
  }

  renderIfConnected() {
    if (this.connected) {
      this.renderComponent()
    }
  }

  renderComponent() {
    render(
      <Counter
        name={this.nameValue}
        initialCount={this.initialCountValue}
        onCountChange={this.handleCountChange}
      />,
      this.element
    )
  }

  handleCountChange = (count) => {
    this.dispatch("count-change", {
      detail: { count },
    })
  }
}
```

The essential line is:

```js
render(<Counter />, this.element)
```

Preact mounts the component inside the controller’s root element. When `renderComponent()` runs again, Preact updates the existing tree instead of recreating everything from scratch.

The `disconnect()` method is just as important. Stimulus calls it when the controller’s element leaves the document. Rendering `null` gives Preact an opportunity to unmount the component and run effect cleanup functions.

Without that step, components containing subscriptions, timers, or document-level event listeners may leak resources.

## Mount it from HTML

Stimulus values make server-rendered data available as typed controller properties:

```html
<div
  data-controller="preact-widget"
  data-preact-widget-name-value="Ada"
  data-preact-widget-initial-count-value="3"
></div>
```

Stimulus converts the attributes into `nameValue` and `initialCountValue`. It also applies the declared types, so the initial count arrives as a number rather than the string `"3"`.

This creates a clean boundary:

- HTML selects where the component appears.
- Stimulus reads and validates DOM configuration.
- Preact renders the interactive interface.
- Custom events communicate changes back to the page.

## Send events back to Stimulus

In the controller, `this.dispatch()` emits a namespaced DOM event. Because the controller is named `preact-widget`, the emitted event is called:

```text
preact-widget:count-change
```

Another Stimulus controller can listen for it directly:

```html
<div
  data-controller="analytics"
  data-action="preact-widget:count-change->analytics#track"
>
  <div
    data-controller="preact-widget"
    data-preact-widget-name-value="Ada"
    data-preact-widget-initial-count-value="3"
  ></div>
</div>
```

The receiving controller can read the event details:

```js
// controllers/analytics_controller.js
import { Controller } from "@hotwired/stimulus"

export default class extends Controller {
  track(event) {
    console.log("New count:", event.detail.count)
  }
}
```

This avoids coupling the Preact component to a particular analytics library or application controller. The component calls a normal callback, while the wrapper converts that callback into a DOM event.

## React to changing values

Stimulus invokes value-change callbacks when corresponding attributes change. That means another part of the application can update the user’s name with ordinary DOM code:

```js
element.dataset.preactWidgetNameValue = "Grace"
```

Stimulus notices the new value, calls `nameValueChanged()`, and the wrapper renders the component again with updated props.

The `connected` flag prevents value callbacks from attempting to render before the controller has completed its connection lifecycle. This matters because Stimulus may invoke change callbacks for initial values during setup.

One detail deserves attention: `initialCount` initializes the component’s local state, but changing that prop later will not reset `useState`. That is normal Preact behavior. If the server must remain the source of truth, make `count` a controlled prop instead:

```jsx
export function Counter({ name, count, onCountChange }) {
  return (
    <section>
      <p>Hello, {name}. The current count is {count}.</p>

      <button type="button" onClick={() => onCountChange(count + 1)}>
        Increment
      </button>
    </section>
  )
}
```

Choose deliberately whether state belongs inside Preact, in a Stimulus controller, or on the server.

## Keep the wrapper thin

A good wrapper controller should mostly perform translation:

- Stimulus values become Preact props.
- Preact callbacks become Stimulus events.
- `connect()` mounts the tree.
- `disconnect()` unmounts it.

Business logic should usually live elsewhere. UI behavior belongs in the Preact component, page-level coordination belongs in Stimulus, and persistence belongs in your application’s data layer.

You can also extract a reusable base controller if many components share this pattern:

```jsx
import { Controller } from "@hotwired/stimulus"
import { render } from "preact"

export default class PreactController extends Controller {
  connect() {
    render(this.component(), this.element)
  }

  disconnect() {
    render(null, this.element)
  }
}
```

A concrete controller then implements `component()`:

```jsx
export default class extends PreactController {
  static values = { name: String }

  component() {
    return <Counter name={this.nameValue} />
  }
}
```

For simple cases, however, an explicit controller is often easier to understand than an abstraction.

Wrapping Preact in Stimulus gives you a practical middle ground: server-rendered pages, HTML-driven composition, and component-level interactivity exactly where you need it.
