# State of the API, October/November 2019

Every few months it's worth stepping back from the framework churn and asking what is actually changing in how we build and consume APIs. Here's where things stand this autumn.

## REST isn't going anywhere

Despite years of "REST is dead" takes, REST over HTTP and JSON is still the default for public APIs. The reason is boring: it's well understood, easy to debug with `curl`, and every language has a client for it.

The real progress is in the tooling around it. OpenAPI 3.x has become the common description format, and most teams I see are moving from hand-written docs to spec-first or spec-generated workflows. A spec gives you docs, mocks, client generation and contract tests from one source of truth. If your API still has no machine-readable description, that's the cheapest upgrade available.

## GraphQL is maturing, not replacing

GraphQL has moved past the hype phase. Large public APIs like GitHub's v4 show it works at scale, and the GraphQL Foundation now gives the spec a neutral home. The conversation has shifted from "should we use GraphQL?" to harder questions:

- **Schema ownership across teams.** Apollo's federation approach, introduced earlier this year, is the most visible attempt to split one graph across services.
- **Query cost and abuse.** Depth limiting, complexity analysis and persisted queries are becoming standard, not optional.
- **Caching.** You give up the free HTTP caching REST offers, so you need a deliberate strategy.

My take: GraphQL shines when you have many clients with different data needs. For a single first-party client talking to a simple backend, it's often more machinery than you need.

## gRPC for the inside, HTTP for the outside

For service-to-service traffic, gRPC and Protocol Buffers keep gaining ground. Strong typing, code generation and streaming are compelling inside a microservice architecture. For anything browser-facing or third-party, plain HTTP APIs still win on accessibility. Many teams now run both: gRPC internally and a REST or GraphQL gateway at the edge.

## The platform underneath is shifting

A few developments worth tracking:

- **Node.js 12 entered LTS** this month and Node 13 shipped, so there's a good reason to review your runtime versions.
- **TypeScript 3.7** landed in early November with optional chaining and nullish coalescing, which cleans up a lot of defensive code in API handlers and clients.
- **HTTP/3 and QUIC** are still in draft form at the IETF, but major CDNs and browsers are already experimenting. You won't need to change your API code, but your latency profile may improve for free.
- **TLS 1.0 and 1.1** are being phased out by the major browsers in early 2020. If you have legacy clients or old load balancer configs, audit them now.

## Security and trust are the real pressure

The biggest forces on API design right now aren't technical fashions. They're privacy and abuse. Platform providers have spent the last year tightening data access, narrowing scopes and deprecating broad endpoints. If you consume third-party APIs, expect more permission reviews and shorter deprecation windows. If you publish one, expect users to ask harder questions about scopes, rate limits and data retention.

Practical checklist:

1. Use least-privilege scopes with OAuth 2.0, and avoid long-lived tokens.
2. Version deliberately and publish a deprecation policy.
3. Rate limit by default and return clear `429` responses with `Retry-After`.
4. Log and monitor for unusual access patterns, not just errors.

## What I'm watching next

- Whether OpenAPI's next minor version improves alignment with JSON Schema.
- How teams handle event-driven APIs (webhooks, WebSockets, AsyncAPI) as real-time features become expected.
- Whether federation patterns settle into something repeatable for GraphQL.

## Wrapping up

The API world in late 2019 is less about picking a winner and more about picking the right tool for each boundary: gRPC inside, REST or GraphQL outside, and a spec describing all of it. Invest in contracts, security and observability, and the protocol choice matters a lot less.
