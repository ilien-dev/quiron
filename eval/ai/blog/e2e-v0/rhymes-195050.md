# State of the API, October/November 2019

APIs hold most modern software together, and the last couple of months brought a few shifts worth catching up on if you've been heads-down shipping features. Here's my roundup of what happened in the API world in October and November 2019.

## GraphQL adoption keeps climbing

GraphQL keeps growing as an alternative to REST, or as a complement to it. More companies are either moving to GraphQL completely or going hybrid. In the hybrid setup a GraphQL layer sits on top of the existing REST services, so front-end teams get more say in how they query data.

I get the appeal. With REST you often hit several endpoints and stitch the responses together, and you still end up fetching too much data or too little. With GraphQL the client asks for exactly the shape of data it needs, in one request. If your front-end has lots of nested data, that can cut both network overhead and front-end complexity.

I wouldn't call it a silver bullet, though. REST gets a lot of caching for free from HTTP semantics, and in GraphQL you have to design that caching yourself. And if your team is new to GraphQL, the learning curve is real. But the tooling (Apollo Client, Apollo Server, Relay and others) has really matured, and moving to GraphQL is easier now than it was even a year or two ago.

## API gateways are becoming standard infrastructure

Microservices keep spreading. For a lot of teams the API gateway has gone from "nice to have" to a standard piece of infrastructure. Kong, AWS API Gateway and Apigee are used more and more often as the default entry point, and they handle authentication, rate limiting, request routing and monitoring for all the backend services.

This makes sense to me. As the number of services grows, you want one consistent layer for the cross-cutting concerns, so you don't have to copy that logic into every service. I'd expect this to keep growing as more teams move to microservices and need some way to manage all the APIs that come with them.

## OpenAPI keeps maturing

The OpenAPI Specification (formerly Swagger) is still the main standard for documenting REST APIs, and the tooling around it keeps growing. Generated documentation, generated client SDKs and contract testing built on OpenAPI specs are all showing up more often in how teams build APIs.

More teams are also going "spec-first". The OpenAPI definition is written before the implementation, and it becomes the contract between front-end and back-end teams, or between a company and the people using its public API, before anyone writes code. I like that. It catches design problems early, and it keeps the docs from drifting away from the real implementation, which has been a problem with API docs for years.

## More focus on API security

High-profile data breaches keep making headlines, so engineering teams and security researchers are paying more attention to API security. OWASP's API Security Top 10 project lists the most common and most damaging API vulnerabilities, and it's getting more attention as teams look for concrete advice on securing their APIs.

Broken object-level authorization, excessive data exposure and missing rate limiting are still among the most common issues found in real API security audits. My guess is that more teams will make API security reviews a normal part of how they build software. Right now it's treated as an afterthought far too often.

## Webhooks and event-driven APIs

Beyond request/response APIs, there's more interest in event-driven architectures. Services talk to each other through events and webhooks and don't make direct, synchronous API calls. That decouples the services more, so the system handles one service going down better and each service is easier to scale on its own.

I'm seeing more tools and platforms with webhook support built in. Standards for structuring event payloads the same way every time, like CloudEvents, are picking up as more companies use event-driven patterns at scale.

## API-first

More companies are also taking an "API-first" view, where the API is treated as a main product and not as a detail behind one specific front-end. One API often has to serve many consumers: web apps, mobile apps, third-party integrations and internal tools. I think designing it as a real product from the start leads to systems that are more flexible and last longer.

This goes hand in hand with the growth of API marketplaces and developer portals, since more companies see their APIs as products that outside developers find, read about and use, and not only as something for internal teams.

## Wrapping up

As I see it, the API world keeps changing at a steady pace. GraphQL keeps growing next to REST (not necessarily replacing it). API gateways are becoming standard for managing a sprawl of services. Security is getting more of the attention it deserves, and event-driven patterns are growing as systems get more distributed.

With the end of the year coming, I'd keep an eye on how these trends develop. It's also a good time to think about where your own team's API strategy could use some of these patterns and tools.
