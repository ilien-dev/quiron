# 10 Minute Tutorial - Full Stack GitHub Authentication with Supabase & React

Authentication is one of those things every app needs, and it's also one of those things nobody really wants to build from scratch. In this tutorial, we'll add GitHub login to a React app using Supabase, and we'll do it in about 10 minutes.

By the end, you'll have:

- A React app where users can sign in with GitHub
- A session that persists across page reloads
- A protected view that only signed-in users can see
- A sign out button

Let's go.

## Step 1: Create a Supabase Project

Head over to [supabase.com](https://supabase.com), sign in, and create a new project. Give it a name and a database password, pick a region, and wait a minute or two for it to spin up.

Once it's ready, go to **Project Settings → API** and grab two values:

- **Project URL**
- **anon public key**

We'll use these in our React app shortly.

## Step 2: Create a GitHub OAuth App

Next, we need to tell GitHub about our app.

1. Go to GitHub **Settings → Developer settings → OAuth Apps → New OAuth App**.
2. Fill in:
   - **Application name:** anything you like
   - **Homepage URL:** `http://localhost:5173`
   - **Authorization callback URL:** this one comes from Supabase. In your Supabase dashboard, go to **Authentication → Providers → GitHub** and copy the callback URL shown there. It looks like `https://<your-project>.supabase.co/auth/v1/callback`.
3. Click **Register application**.
4. Copy the **Client ID**, then generate and copy a **Client Secret**.

Now back in Supabase, under **Authentication → Providers → GitHub**, enable the provider, paste in the Client ID and Client Secret, and save.

Finally, under **Authentication → URL Configuration**, make sure `http://localhost:5173` is set as the Site URL (or added to the redirect URLs).

That's all the configuration. Now for the code.

## Step 3: Create the React App

We'll use Vite:

```bash
npm create vite@latest supabase-github-auth -- --template react
cd supabase-github-auth
npm install
npm install @supabase/supabase-js
```

Create a `.env` file in the root of the project:

```bash
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-anon-key
```

## Step 4: Create the Supabase Client

Create a new file at `src/supabaseClient.js`:

```javascript
import { createClient } from '@supabase/supabase-js';

export const supabase = createClient(
  import.meta.env.VITE_SUPABASE_URL,
  import.meta.env.VITE_SUPABASE_ANON_KEY
);
```

The anon key is safe to use in the browser. Supabase uses Row Level Security on the database side to control what each user can actually access.

## Step 5: Build the App

Now open `src/App.jsx` and replace its contents with this:

```jsx
import { useEffect, useState } from 'react';
import { supabase } from './supabaseClient';

function App() {
  const [session, setSession] = useState(null);

  useEffect(() => {
    // Get the current session on load
    supabase.auth.getSession().then(({ data: { session } }) => {
      setSession(session);
    });

    // Listen for sign in / sign out
    const {
      data: { subscription },
    } = supabase.auth.onAuthStateChange((_event, session) => {
      setSession(session);
    });

    return () => subscription.unsubscribe();
  }, []);

  async function signInWithGitHub() {
    const { error } = await supabase.auth.signInWithOAuth({
      provider: 'github',
    });
    if (error) console.error(error.message);
  }

  async function signOut() {
    await supabase.auth.signOut();
  }

  if (!session) {
    return (
      <div style={{ padding: 40 }}>
        <h1>Welcome</h1>
        <button onClick={signInWithGitHub}>Sign in with GitHub</button>
      </div>
    );
  }

  const { user } = session;

  return (
    <div style={{ padding: 40 }}>
      <h1>Hello, {user.user_metadata.user_name}!</h1>
      <img
        src={user.user_metadata.avatar_url}
        alt="avatar"
        width={80}
        style={{ borderRadius: '50%' }}
      />
      <p>Signed in as {user.email}</p>
      <button onClick={signOut}>Sign out</button>
    </div>
  );
}

export default App;
```

Let's walk through what's happening here.

**`getSession()`** checks whether there's already a signed-in user when the app loads. Supabase stores the session in local storage, so users stay logged in after a refresh.

**`onAuthStateChange()`** subscribes to auth events. When the user comes back from GitHub, Supabase picks up the tokens from the URL, creates the session, and fires this listener. We just update our state.

**`signInWithOAuth({ provider: 'github' })`** redirects the user to GitHub to authorize the app. After they approve, GitHub sends them back to Supabase, and Supabase sends them back to your app.

**`signOut()`** clears the session, which also triggers the listener, so the UI flips back to the sign-in screen.

## Step 6: Run It

```bash
npm run dev
```

Open `http://localhost:5173`, click **Sign in with GitHub**, approve the app, and you should land back on your page with your GitHub username and avatar showing. Refresh the page and you'll still be signed in.

You can also check the **Authentication → Users** section of your Supabase dashboard. Your new user will be listed there.

## Bonus: Using the User in Your Database

The "full stack" part really shines once you start storing data. Say you have a `notes` table with a `user_id` column. You can enable Row Level Security and add a policy like this in the SQL editor:

```sql
alter table notes enable row level security;

create policy "Users can manage their own notes"
on notes
for all
using (auth.uid() = user_id)
with check (auth.uid() = user_id);
```

Now, from your React app, a query like this will only ever return the signed-in user's notes:

```javascript
const { data } = await supabase.from('notes').select('*');
```

No backend code, no custom API. The database itself enforces who can see what.

## Wrapping Up

In about 10 minutes, we:

1. Created a Supabase project
2. Registered a GitHub OAuth app
3. Wired up sign in, sign out, and session persistence in React
4. Saw how Row Level Security ties users to their data

From here, you could add more providers like Google or Discord (it's the same flow, just a different `provider` value), add routing with protected pages, or start building out your data model.
