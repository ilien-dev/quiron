# Why Turborepo Will Be the First Big Trend of 2022

Every year in JavaScript has a theme. 2020 was the year of Jamstack going mainstream. 2021 was the year of Rust-powered tooling: esbuild, SWC, and friends made us realize our build tools had been leaving a lot of speed on the table.

I think 2022 is going to be the year of the monorepo going mainstream, and Turborepo is going to be the thing that gets it there.

Vercel announced it had acquired Turborepo in December 2021, and the timing couldn't be better. Here's why I think it's about to take off.

## Monorepos were always a good idea

The case for monorepos isn't new. Google, Meta, and Microsoft have run massive monorepos for years. The benefits are pretty clear:

- **Atomic changes.** Update a shared library and all its consumers in one commit.
- **Code sharing without publishing.** No more bumping versions of an internal package on npm just to use a fix in another app.
- **Consistent tooling.** One lint config, one TypeScript setup, one CI pipeline.
- **Easier refactoring.** You can see everywhere a function is used, across every project.

For JavaScript teams, the typical setup looks something like this:

```
apps/
  web/
  docs/
  admin/
packages/
  ui/
  utils/
  eslint-config/
  tsconfig/
```

Multiple apps sharing multiple internal packages. Pretty common, especially as companies grow.

## But monorepos were painful

The problem has never been the idea. It's been the tooling.

Once your monorepo grows past a handful of packages, things slow down. Run `build` across everything and you're rebuilding packages that haven't changed. CI runs every test for every package on every pull request. Local development gets sluggish. Dependency ordering becomes a headache: you need to build `utils` before `ui`, and `ui` before `web`, and so on.

There have been tools to address this. **Lerna** was the classic choice for years, but it focused more on publishing than on fast task running, and it went largely unmaintained for a while. **Nx** is powerful and has been solving these problems for a long time, but many developers found it heavy, with a lot of concepts and configuration to learn upfront. **Bazel** is incredibly capable but notoriously complex to set up for a JS project. And Yarn, npm, and pnpm **workspaces** handle linking packages together, but don't really help with running tasks efficiently.

So most teams ended up with a patchwork of workspace config, custom scripts, and a lot of waiting.

## What Turborepo does differently

Turborepo is a high-performance build system for JavaScript and TypeScript monorepos. It sits on top of your existing package manager workspaces and focuses on one thing: running your tasks as fast as possible.

It does that with a few key ideas.

### 1. It never does the same work twice

Turborepo hashes the inputs to each task: the source files, dependencies, environment variables, and config. If it has seen that exact hash before, it skips the task entirely and replays the cached output and logs.

That means if you run `turbo run build`, change one file in `apps/docs`, and run it again, only `docs` rebuilds. Everything else comes from cache in milliseconds.

### 2. Remote caching

This is where it gets really interesting. The cache doesn't have to live only on your machine. With remote caching, your team and your CI share a single cache.

If your teammate already built a commit, you don't need to. If CI already ran tests on a branch, running them locally is instant. For large teams, this can cut a huge amount of redundant compute. Given that Vercel now owns Turborepo, it's no surprise that remote caching integrates smoothly with Vercel, but you can also self-host it.

### 3. It understands your dependency graph

Turborepo reads your workspace to figure out how packages depend on each other. Then you describe how tasks relate in a small config file:

```json
{
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": []
    },
    "lint": {
      "outputs": []
    },
    "dev": {
      "cache": false
    }
  }
}
```

The `^build` means "build my dependencies first." With that, Turborepo builds a task graph and runs everything in the correct order, in parallel wherever possible, using all your CPU cores.

### 4. It's incremental to adopt

This might be the biggest reason I think it'll spread fast. You don't have to restructure your repo or learn a new philosophy. If you already have a workspace-based monorepo, adding Turborepo is roughly:

```bash
npm install turbo -D
```

Add a `turbo.json`, change your root scripts to `turbo run build`, and you're done. Your packages keep their own `package.json` scripts. Turborepo just orchestrates them.

It's written in Go (with the Rust-y trend pushing further on the horizon), so it's fast to start up and fast to run.

## Why now?

Good tools come out all the time without becoming trends. So why do I think Turborepo specifically will break out in 2022?

**The problem is universal.** Almost every company that's past a certain size has either a monorepo that's getting slow, or a collection of polyrepos that are painful to keep in sync. Turborepo has an answer for both.

**Vercel's distribution.** Vercel has a big developer audience, strong DX-focused marketing, and it owns Next.js. Official Next.js examples and starter templates using Turborepo are a natural next step. When a framework as popular as Next.js points people to a tool, adoption follows.

**The timing with Rust/Go tooling.** Developers are primed to care about build speed right now. esbuild and SWC made "your builds could be 10x faster" a believable pitch. Turborepo rides the same wave.

**Low barrier to entry.** Compared to Nx or Bazel, the learning curve is small. You can explain what it does in one sentence: "It caches your npm scripts and runs them in the right order." That kind of simplicity spreads.

**Design systems and shared packages are everywhere.** More teams than ever are maintaining internal component libraries shared across several apps. That's exactly the setup where monorepo tooling pays off.

## The caveats

To be fair, Turborepo isn't a silver bullet.

- It's young. Expect rough edges, missing features, and breaking changes.
- It doesn't do code generation, dependency constraints, or project graph visualization to the degree Nx does. If you need those, Nx is still a very strong option.
- Caching is only as good as your configuration. If you forget to declare an environment variable or an output folder, you can get stale cache hits.
- Monorepos still bring their own challenges around ownership, permissions, and repo size that no build tool fully solves.

## My prediction

By the end of 2022, I expect we'll see:

- Turborepo as the default in a lot of new monorepo starters and templates
- More companies consolidating polyrepos into monorepos because the tooling finally makes it painless
- Competition heating up, with other monorepo tools doubling down on speed and simplicity
- "Remote caching" becoming a checklist feature that developers expect from their build tools

Monorepos have been the right architecture for a lot of teams for a long time. Turborepo might be the tool that finally makes them easy enough for everyone else.

If you have a monorepo that's getting slow, give it an afternoon. I think you'll be surprised.
