# State of the API, October/November 2019

APIs are still what holds most software together, and the last couple of months brought a few shifts worth catching up on if you've been heads-down shipping features. Here's what happened in the API world in October and November 2019.

## GraphQL adoption keeps climbing

GraphQL keeps gaining ground as an alternative (or a complement) to plain REST APIs. More companies are either moving to GraphQL entirely or going hybrid: they put a GraphQL layer over their existing REST services so front-end teams get more say in how they query data.

The appeal is easy to see. With REST you often hit several endpoints and stitch the responses together, and you get too much data from one and not enough from another. GraphQL lets the client ask for exactly the shape of data it needs in a single request. If your front-end deals with lots of nested data, that can cut network overhead and make the front-end code a lot simpler.

GraphQL isn't a silver bullet, though. REST gets a lot of caching for free from HTTP semantics. In GraphQL it has to be designed on purpose. And the learning curve for teams that are new to it is real. Still, the tooling (Apollo Client, Apollo Server, Relay and others) has grown up a lot, and adopting it is easier than it was even a year or two ago.

## API gateways are becoming standard infrastructure

As more teams split things into microservices, the API gateway has gone from "nice to have" to a standard piece of infrastructure. Kong, AWS API Gateway and Apigee are more and more often the default entry point. They take care of authentication, rate limiting, routing and monitoring for a whole fleet of backend services.

It makes sense. The more services you have, the more you need one layer that handles the cross-cutting concerns, instead of the same logic copied into every service. I'd expect this to speed up as more teams move to microservices and need some way to manage the API sprawl that comes with them.

## OpenAPI keeps growing up

The OpenAPI Specification (formerly Swagger) is still the main standard for documenting REST APIs, and the tooling around it keeps growing. Docs and client SDKs generated from OpenAPI specs are now a normal part of how a lot of teams build APIs, and so are contract tests built on them.

More teams are also going "spec-first". They write the OpenAPI definition before the implementation, and it becomes the contract between front-end and back-end teams, or between a company and the people using its public API, before anyone writes code. That's how design problems get caught early. It also keeps the docs from drifting away from what the code does, which has been a problem with API docs for years.

## More attention on API security

Data breaches keep making headlines, and API security is getting more attention from engineering teams and security researchers. The OWASP API Security Top 10 project, which lists the most common and damaging API vulnerabilities, is getting noticed as teams look for concrete advice on hardening their APIs.

Broken object-level authorization, excessive data exposure and missing rate limits are still among the most common problems found in real API security audits. I think more teams will make API security reviews a normal step in how they build software, and stop treating security as an afterthought.

## Webhooks and event-driven APIs

Outside plain request/response, there's growing interest in event-driven systems, where services talk through events and webhooks instead of calling each other directly and waiting. Services depend on each other less. One service going down hurts the others less, and each one can scale on its own.

More tools and platforms now ship with webhook support built in. Standards for how to structure event payloads, like CloudEvents, are picking up too, as more companies use event-driven patterns at scale.

## API-first development

More companies are going "API-first": the API is treated as a product in its own right, not as a detail behind one particular front-end. One API often has to serve web apps, mobile apps, third-party integrations and internal tools all at once, and if you design it as a product from day one you get something more flexible that lasts longer.

This ties into the growth of API marketplaces and developer portals. More companies treat their APIs as products that outside developers should be able to find and use, and not only their own teams. That means they're documented for strangers.

## What to watch

GraphQL is growing next to REST, and it isn't necessarily replacing it. Gateways are turning into the standard way to keep service sprawl under control. Security's getting more of the attention it deserves. Event-driven patterns are catching on as systems get more distributed.

We're heading into the end of the year, so it's a good time to look at where your own team's APIs could use some of these.
