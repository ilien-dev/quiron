Passwords are a poor fit for many apps. Users reuse them, forget them, and abandon sign-up when asked to create one. Magic links remove the password entirely: the user enters an email address, receives a one-time link, clicks it, and is signed in. Supabase Auth supports this out of the box, and with Next.js's App Router you can wire it into both the server and the client in a way that keeps protected routes actually protected.

This post walks through a complete setup: sending the magic link, handling the callback, refreshing sessions in middleware, and gating routes on the server. The examples use the `@supabase/ssr` package, which is the current recommended way to share auth cookies between Next.js and Supabase.

## What we're building

- A login page where the user enters an email address
- A `/auth/callback` route that exchanges the link's code for a session
- Middleware that refreshes the session on every request
- A protected `/dashboard` route group that redirects anonymous visitors
- A sign-out action

The principle throughout: **the server decides who is allowed in, not the client.** Hiding a button in React is a UI choice. Access control has to happen where the data is fetched.

## Step 1: Environment and clients

Start with the two environment variables from your Supabase project settings:

```bash
# .env.local
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=your-anon-key
```

The anon key is designed to be public. Row Level Security is what protects your data, so keep RLS enabled on any table you create.

Next, create a helper for server components, route handlers, and server actions. Cookies are read and written through Next.js's `cookies()` API:

```ts
// lib/supabase/server.ts
import { createServerClient } from "@supabase/ssr";
import { cookies } from "next/headers";

export async function createClient() {
  const cookieStore = await cookies();

  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return cookieStore.getAll();
        },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) =>
              cookieStore.set(name, value, options)
            );
          } catch {
            // Called from a Server Component, where cookies are read-only.
            // The middleware will refresh the session instead.
          }
        },
      },
    }
  );
}
```

The `try/catch` matters. Server Components can read cookies but cannot set them, so the write will throw there. Middleware handles the refresh, so swallowing the error in this specific case is safe.

And a browser client for the login form:

```ts
// lib/supabase/client.ts
import { createBrowserClient } from "@supabase/ssr";

export function createClient() {
  return createBrowserClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!
  );
}
```

## Step 2: Sending the magic link

The login page is a client component that calls `signInWithOtp`. The `emailRedirectTo` option tells Supabase where to send the user after they click the link.

```tsx
// app/login/page.tsx
"use client";

import { useState } from "react";
import { createClient } from "@/lib/supabase/client";

export default function LoginPage() {
  const [email, setEmail] = useState("");
  const [status, setStatus] = useState<"idle" | "sending" | "sent" | "error">("idle");

  async function handleSubmit(e: React.FormEvent) {
    e.preventDefault();
    setStatus("sending");

    const supabase = createClient();
    const { error } = await supabase.auth.signInWithOtp({
      email,
      options: {
        emailRedirectTo: `${window.location.origin}/auth/callback?next=/dashboard`,
      },
    });

    setStatus(error ? "error" : "sent");
  }

  if (status === "sent") {
    return <p>Check your inbox. The link expires shortly.</p>;
  }

  return (
    <form onSubmit={handleSubmit}>
      <label htmlFor="email">Email</label>
      <input
        id="email"
        type="email"
        required
        value={email}
        onChange={(e) => setEmail(e.target.value)}
      />
      <button type="submit" disabled={status === "sending"}>
        {status === "sending" ? "Sending..." : "Send magic link"}
      </button>
      {status === "error" && <p>Something went wrong. Try again.</p>}
    </form>
  );
}
```

Two details are worth noting. First, the `next` parameter lets you return the user to the page they originally wanted. In a real app, validate it: only accept relative paths that start with a single `/`, so the callback can't be used to redirect users to an external site.

Second, don't reveal whether an email is registered. Supabase does not create a separate "user not found" leak here by default, and your UI should show the same "check your inbox" message regardless of the outcome.

## Step 3: The callback route

When the user clicks the link, they land on `/auth/callback` with a `code` query parameter. A route handler exchanges that code for a session and writes the auth cookies:

```ts
// app/auth/callback/route.ts
import { NextResponse } from "next/server";
import { createClient } from "@/lib/supabase/server";

export async function GET(request: Request) {
  const { searchParams, origin } = new URL(request.url);
  const code = searchParams.get("code");
  const rawNext = searchParams.get("next") ?? "/dashboard";

  // Only allow same-origin relative paths.
  const next = rawNext.startsWith("/") && !rawNext.startsWith("//")
    ? rawNext
    : "/dashboard";

  if (code) {
    const supabase = await createClient();
    const { error } = await supabase.auth.exchangeCodeForSession(code);

    if (!error) {
      return NextResponse.redirect(`${origin}${next}`);
    }
  }

  return NextResponse.redirect(`${origin}/login?error=invalid_link`);
}
```

This is a route handler, not a page, because it needs to set cookies and then redirect. The `//` check guards against protocol-relative URLs like `//evil.example`, which would otherwise pass a simple `startsWith("/")` test.

## Step 4: Middleware for session refresh

Supabase access tokens are short-lived. Without intervention, a user who keeps the tab open will eventually get logged out for no visible reason. Middleware fixes this by refreshing the session on each request and writing updated cookies back to the response.

```ts
// lib/supabase/middleware.ts
import { createServerClient } from "@supabase/ssr";
import { NextResponse, type NextRequest } from "next/server";

export async function updateSession(request: NextRequest) {
  let response = NextResponse.next({ request });

  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return request.cookies.getAll();
        },
        setAll(cookiesToSet) {
          cookiesToSet.forEach(({ name, value }) =>
            request.cookies.set(name, value)
          );
          response = NextResponse.next({ request });
          cookiesToSet.forEach(({ name, value, options }) =>
            response.cookies.set(name, value, options)
          );
        },
      },
    }
  );

  // Do not put logic between createServerClient and getUser().
  const {
    data: { user },
  } = await supabase.auth.getUser();

  return { response, user };
}
```

Use `getUser()` rather than `getSession()` here. `getSession()` reads the session from cookies without verifying it with the Auth server, so it can be spoofed. `getUser()` validates the token on every call, which is what you want for access decisions.

Now wire it into the root middleware:

```ts
// middleware.ts
import { type NextRequest, NextResponse } from "next/server";
import { updateSession } from "@/lib/supabase/middleware";

const PROTECTED_PREFIXES = ["/dashboard", "/settings"];

export async function middleware(request: NextRequest) {
  const { response, user } = await updateSession(request);
  const { pathname } = request.nextUrl;

  const isProtected = PROTECTED_PREFIXES.some((prefix) =>
    pathname.startsWith(prefix)
  );

  if (isProtected && !user) {
    const loginUrl = new URL("/login", request.url);
    loginUrl.searchParams.set("next", pathname);
    return NextResponse.redirect(loginUrl);
  }

  if (pathname === "/login" && user) {
    return NextResponse.redirect(new URL("/dashboard", request.url));
  }

  return response;
}

export const config = {
  matcher: [
    // Skip static assets and image optimization.
    "/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)",
  ],
};
```

There's a subtle point here: when you return a redirect instead of `response`, the refreshed cookies set on `response` are lost. In most setups this is harmless because the user is redirected to a page that doesn't need the new session, but if you hit a refresh-loop bug, copy cookies from `response` onto the redirect.

## Step 5: Defense in depth on the server

Middleware is the first gate, not the only one. It runs at the edge, it can be bypassed by misconfigured matchers, and it's easy to forget when you add a new route. Check the user again wherever you touch protected data.

```tsx
// app/dashboard/layout.tsx
import { redirect } from "next/navigation";
import { createClient } from "@/lib/supabase/server";

export default async function DashboardLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const supabase = await createClient();
  const {
    data: { user },
  } = await supabase.auth.getUser();

  if (!user) {
    redirect("/login");
  }

  return <section>{children}</section>;
}
```

And for data access, rely on RLS so the database enforces ownership even if application code has a bug:

```sql
alter table notes enable row level security;

create policy "Users manage their own notes"
on notes
for all
using (auth.uid() = user_id)
with check (auth.uid() = user_id);
```

With this policy, a query from an authenticated user can only read or write rows where `user_id` matches their own ID. The `with check` clause covers inserts and updates, so users can't create rows owned by someone else.

## Step 6: Sign out

Sign-out is a server action, which keeps the cookie mutation on the server:

```ts
// app/actions/auth.ts
"use server";

import { redirect } from "next/navigation";
import { createClient } from "@/lib/supabase/server";

export async function signOut() {
  const supabase = await createClient();
  await supabase.auth.signOut();
  redirect("/login");
}
```

Call it from a form with a submit button, which works without JavaScript and avoids a client-side fetch.

## Common pitfalls

**Redirect URLs not allowlisted.** If the magic link opens a Supabase error page instead of your app, check the Redirect URLs list in the Supabase dashboard. Add your local and production callback URLs explicitly.

**Links opened in a different browser.** The PKCE flow stores a verifier in the browser that started the sign-in. Clicking the link in a different browser or an in-app mail viewer that opens a separate context can fail the exchange. Show a clear error and let the user request a new link.

**Scanners consuming the link.** Some email providers pre-fetch links to check for malware, which can consume a one-time code before the user clicks. If users report "invalid link" errors right after requesting one, this is a likely cause. Some apps mitigate it by showing an intermediate page with a button that performs the exchange.

**Forgetting the matcher.** If your middleware matcher excludes a protected path, that path is unprotected at the edge. The server-side check in the layout still catches it, which is one more reason to keep both layers.

## Wrapping up

Magic links give you a password-free sign-in that users tend to find easier than a traditional form. With Supabase handling token issuance and `@supabase/ssr` handling cookies, the remaining work is in the routing: a callback that exchanges the code safely, middleware that keeps sessions fresh and gates protected paths, and server-side checks that don't trust the client.

The principle to carry forward is simple. Middleware gives you a fast, early redirect. Layouts and route handlers confirm identity where data lives. RLS enforces ownership at the database. Each layer can fail, so you want more than one.

If you build on this, start with the callback and the RLS policies, since those are the parts that are easiest to get subtly wrong. Then test the flow end to end with a real inbox, because email is where most real-world surprises show up.
