Every year the JavaScript ecosystem picks a handful of tools to obsess over. In 2020 it was Snowpack and the "unbundled" dev server. In 2021 it was Vite and esbuild, which made us all realize how slow our tooling had become. My bet for the first big obsession of 2022 is **Turborepo**.

If you missed the news: in December 2021, Vercel acquired Turborepo, a high-performance build system for JavaScript and TypeScript monorepos created by Jared Palmer (of Formik and TSDX fame). Alongside the acquisition, Turborepo went open source and shipped version 1.0.

That alone would get it some attention. But I think there's more going on here than one acquisition headline. Turborepo shows up at the moment when a lot of teams are feeling monorepo pain, the incumbent tools are showing their age, and the company behind it has a track record of turning developer tools into defaults. Here's why I think it takes off.

## The Problem: Monorepos Are Great Until They're Slow

Monorepos have quietly become the standard way to organize serious JavaScript projects. Next.js, Babel, Jest, React, and many design systems and SaaS frontends all live in monorepos. The appeal is obvious:

- **Shared code without publishing ceremony.** Your `ui` package and your `web` app live side by side. Change a button, see it in the app immediately.
- **Atomic changes.** One pull request can update an API client and every consumer of it.
- **One set of tooling.** One ESLint config, one TypeScript setup, one CI pipeline.

The problem comes later. Your repo grows to 10, 20, 50 packages. Every `npm run build` rebuilds everything. CI takes 25 minutes even if you changed a single README. Engineers start skipping local test runs because they take too long. The things that made the monorepo pleasant start making it painful.

Package managers like Yarn, npm 7+, and pnpm solved the *dependency* side with workspaces. They link your local packages together and dedupe `node_modules`. What they don't solve is the *task* side: figuring out what needs to be built, in what order, and whether it needs to be built at all.

That's the gap Turborepo fills.

## What Turborepo Actually Does

Turborepo is a build system that sits on top of your existing workspaces. It doesn't replace npm, Yarn, or pnpm, and it doesn't ask you to rewrite your build scripts. It orchestrates the scripts you already have.

Its core ideas are simple:

### 1. It never does the same work twice

Turborepo hashes the inputs of each task: the source files, dependencies, environment, and the task configuration. If it has seen that exact hash before, it skips the task entirely and restores the cached output and logs. You get "build complete" in milliseconds instead of minutes.

This is the same idea that has made Bazel popular at Google-scale companies, but without asking you to write BUILD files in Starlark.

### 2. It understands your dependency graph

Turborepo reads your workspace and knows that `web` depends on `ui`, which depends on `tsconfig`. When you run a build, it builds things in topological order and runs everything that *can* run in parallel at the same time, using all your CPU cores.

### 3. It can share the cache across machines

This is the killer feature. With **Remote Caching**, the cache isn't limited to your laptop. If your teammate already built the commit you just pulled, or CI already built it, you download the result instead of rebuilding it. Vercel offers this as a hosted service, and because the cache API is just HTTP, teams can also self-host.

Picture what that means for CI: a pull request that touches one package only rebuilds that package and its dependents. Everything else is a cache hit.

## Setting It Up Takes Minutes

Here's the part that I think will drive adoption more than anything: the barrier to entry is tiny.

You can scaffold a fresh monorepo with:

```bash
npx create-turbo@latest
```

Or add it to an existing workspace. Install it as a dev dependency:

```bash
npm install turbo -D
```

Then describe your pipeline in your root `package.json`:

```json
{
  "name": "my-monorepo",
  "private": true,
  "workspaces": ["apps/*", "packages/*"],
  "scripts": {
    "build": "turbo run build",
    "test": "turbo run test",
    "lint": "turbo run lint",
    "dev": "turbo run dev --parallel"
  },
  "devDependencies": {
    "turbo": "latest"
  },
  "turbo": {
    "pipeline": {
      "build": {
        "dependsOn": ["^build"],
        "outputs": ["dist/**", ".next/**"]
      },
      "test": {
        "dependsOn": ["build"],
        "outputs": []
      },
      "lint": {
        "outputs": []
      },
      "dev": {
        "cache": false
      }
    }
  }
}
```

Let's unpack that config:

- `"dependsOn": ["^build"]` means "before building this package, build all of its dependencies first." The `^` refers to upstream workspace dependencies.
- `"dependsOn": ["build"]` (no caret) on `test` means "build this same package before testing it."
- `outputs` tells Turborepo which files to cache and restore.
- `"cache": false` on `dev` makes sense because you never want to cache a long-running dev server.

That's it. Your existing `build`, `test`, and `lint` scripts in each package stay exactly as they are. Run `npm run build` once and it does the work. Run it again without changes and you'll see something like:

```
>>> FULL TURBO
```

That message is going to be in a lot of screenshots this year.

To turn on remote caching with Vercel:

```bash
npx turbo login
npx turbo link
```

## Why 2022, and Why Turborepo?

Monorepo tooling isn't new. So why do I think this one breaks out now?

### The incumbents leave room

**Lerna** was the default JavaScript monorepo tool for years, but development has slowed considerably, and much of what it did is now handled by package manager workspaces. A lot of teams use Lerna today mainly out of inertia.

**Nx** is powerful and has excellent caching and graph tooling, but it's also a larger, more opinionated system with plugins, generators, and its own way of doing things. Many teams love that; others want something lighter.

**Bazel** and **Rush** are proven at scale but come with steep learning curves that most frontend teams won't climb.

Turborepo slots into a clear position: *incremental, cached, parallel builds with almost no configuration and no lock-in*. If you decide you don't like it, you delete a config block and a dev dependency. That's a very easy sell to a skeptical tech lead.

### It's fast because it isn't written in JavaScript

Turborepo is written in Go. That follows the same pattern that made esbuild (Go) and SWC (Rust) the breakout tools of the last year or two: the JavaScript community has accepted that our tooling doesn't have to be written in JavaScript, and that native-speed tools feel dramatically better. Turborepo rides that wave.

### Vercel knows how to drive adoption

Vercel took Next.js from "a neat React framework" to one of the most widely used ways to build React apps. They have the docs team, the developer relations machine, the conference stage, and the hosting platform to make Turborepo a first-class experience. Expect deeper integration with Vercel deployments, templates that use Turborepo by default, and lots of content showing off cache hit rates.

There's a business logic here too: remote caching is a natural paid feature, which means Vercel has a direct incentive to keep investing in it.

### CI costs are finally getting attention

As teams grow, CI minutes become a real line item, and slow pipelines become a real productivity tax. A tool that can credibly cut CI times dramatically on day one is going to get noticed by engineering managers, not just engineers who like shiny things.

## What to Watch Out For

I'm optimistic, but it's worth being honest about the rough edges of a 1.0:

- **Cache correctness depends on your config.** If you forget to list an output directory or an environment variable that affects your build, you can get stale results. Read the docs on hashing and environment variables carefully.
- **It's a task runner, not a full platform.** It won't generate code, enforce module boundaries, or visualize architecture the way Nx can. If you need those features, Turborepo alone may not be enough.
- **The ecosystem is young.** Expect breaking changes, missing features, and some GitHub issues without answers yet. Pin your version.
- **Remote caching means trusting a cache.** For sensitive projects, think about where your build artifacts are stored, and consider self-hosting.

None of these are deal breakers. They're the normal trade-offs of adopting a fresh tool early.

## Should You Try It?

If you have a JavaScript or TypeScript monorepo with more than a few packages, and your builds or CI feel slow, I'd say yes. The cost of trying it is an afternoon. The worst case is you remove it. The best case is your CI times drop significantly and your team stops dreading `npm run build`.

If you're starting a new project with multiple apps or shared packages, run `npx create-turbo@latest` and look at the structure it gives you. Even if you don't adopt it, it's a clean reference for how a modern monorepo can be organized.

My prediction: by the end of 2022, Turborepo will be in a lot of `package.json` files, "FULL TURBO" will be a meme, and we'll all wonder how we put up with rebuilding the same unchanged packages over and over.
