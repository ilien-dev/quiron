# State of the API, October/November 2019

If you've been heads-down shipping features for the past couple of months, here's a roundup of what's been going on in the API world in October and November 2019.

## GraphQL keeps climbing

GraphQL keeps gaining ground as an alternative to REST (or as a complement to it). Some companies are moving to it entirely. Others go hybrid and put a GraphQL layer on top of their existing REST services, so front-end teams get more say in how they query data.

The appeal is easy to see: instead of hitting a bunch of REST endpoints and stitching the responses together, or dealing with over-fetching and under-fetching, the client asks for exactly the shape of data it needs in a single request. If your front-end has lots of nested data relationships, that can cut down on network overhead and on front-end code too.

It's not a silver bullet though. With REST you get caching more or less for free (thanks to HTTP semantics). With GraphQL you have to design for it. And the learning curve is real if your team is new to it. The tooling (Apollo's client and server, Relay and so on) has grown up a lot, so adopting it is easier than it was even a year or two ago.

## API gateways are now just part of the stack

As more teams split things into microservices, API gateways went from "nice to have" to a standard piece of infrastructure. Kong, AWS API Gateway and Apigee are more and more often the default entry point for a whole fleet of backend services. They take care of authentication and rate limiting, route the requests and monitor them.

It makes sense. The more services you have, the more you need one place for those cross-cutting concerns, instead of copying the same logic in every service. I expect this to speed up as more teams go the microservices route and need a way to keep the resulting API sprawl under control.

## OpenAPI and spec-first

The OpenAPI Specification (it used to be called Swagger) is still the main standard for documenting REST APIs, and the tools around it keep growing. Auto-generated docs, client SDK generation and contract testing on top of OpenAPI specs are all becoming a normal part of how APIs get built.

More teams are also going "spec-first": you write the OpenAPI definition before the implementation, and it's the contract between front-end and back-end teams (or between a company and the people using its public API) before anyone writes code. You catch design problems early. And the docs don't drift away from what the code actually does, which has plagued API docs for years.

## More eyes on security

Data breaches keep making the news, so engineering teams and security researchers are paying more attention to API security. OWASP's API Security Top 10 project, a catalog of the most common and most damaging API vulnerabilities, is getting more visible as teams look for concrete advice on how to harden their APIs.

Broken object-level authorization, excessive data exposure and missing rate limiting are still among the most common issues found in real-world API security audits. I expect more teams to make security reviews a standard step of their development process, and not something they think about at the end.

## Webhooks, events and API-first

Outside of plain request/response, there's growing interest in event-driven architectures, where services talk to each other through events and webhooks instead of direct, synchronous calls. The services are less coupled that way. One of them going down doesn't take the rest with it, and each can scale on its own. More platforms offer webhook support out of the box, and standards for giving event payloads a consistent structure (like CloudEvents) are getting traction as more companies use these patterns at scale.

The last one is more of a mindset: more companies go "API-first" and treat the API as a product, not as an implementation detail behind one specific front-end. A single API often has to serve web and mobile apps plus third-party integrations and internal tools. Design it as a real product from day one and it holds up better later on. This also goes hand in hand with API marketplaces and developer portals: companies want outside developers to find their APIs and use them (docs included), not only their own teams.
