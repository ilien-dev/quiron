# State of the API, October/November 2019

A few things moved in the API world over the last couple of months. If you've been heads-down shipping features, here's what happened in October and November 2019.

## GraphQL keeps growing

More companies are moving to GraphQL, which is growing next to REST and not necessarily in place of it. Some go all the way, others put a GraphQL layer on top of the REST services they already have so front-end teams get more say in how they ask for data. With REST you often hit several endpoints and stitch the responses together, and you get back too much data or too little. GraphQL lets the client ask for exactly the shape it wants in one request, and if your front end has a lot of nested data that can cut both network traffic and the code you write to glue things together.

It has costs. REST gets you caching more or less for free from HTTP, while in GraphQL you have to design it yourself, and the learning curve for a team that's new to it is real. The tools have grown up a lot in the last year or two (Apollo Client, Apollo Server, Relay and others), so getting started is easier than it used to be.

## API gateways are now just infrastructure

As more teams split things into microservices, the API gateway went from "nice to have" to a standard piece of the stack. Kong, AWS API Gateway and Apigee are more and more often the front door that handles auth, rate limiting, routing and monitoring for a whole fleet of backend services. That makes sense. Once you have enough services, you want one place for the things every service needs instead of copying the same logic into each of them. I'd expect this to keep going as more teams take on microservices and end up with API sprawl to manage.

## OpenAPI and spec-first

The OpenAPI Specification (it used to be called Swagger) is still the main way people document REST APIs, and there are more tools built on it every month. Generated docs, generated client SDKs and contract tests built from the spec are becoming a normal part of how teams work.

More teams are also going "spec-first". They write the OpenAPI definition before any code. The spec is then the contract between the front-end and back-end teams, and for a public API it's the contract between a company and the developers who call it. That catches design problems early and it stops the docs from drifting away from what the code actually does, which has been a problem with API docs for years.

## Security

Big data breaches keep making the news. As a result engineering teams and security researchers alike are paying more attention to API security. The OWASP API Security Top 10 project lists the most common and damaging API vulnerabilities, and it's getting noticed by teams who want concrete advice on hardening their APIs. The usual problems found in real audits are still broken object-level authorization, APIs that return more data than they should, and missing rate limits. I'd expect more teams to make an API security review a normal step in development and stop treating it as an afterthought.

## Webhooks and events

There's also more interest in event-driven designs, where services talk through events and webhooks instead of calling each other's APIs directly and waiting for an answer. Services depend on each other less. One going down hurts the rest less, and each one can scale on its own. More platforms ship webhook support out of the box, and standards for a consistent event payload format, like CloudEvents, are picking up as more companies use events at scale.

## API-first

"API-first" is spreading too: the API is treated as a product in its own right, not as a detail behind one particular front end. One API often has to serve a web app, a mobile app, third-party integrations and internal tools at once. Designed as a product from day one, it holds up better. This goes hand in hand with the growth of API marketplaces and developer portals, where companies put their APIs out for outside developers to find and use.
