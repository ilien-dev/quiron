# Repasando Artículos: Monads For Functional Programming

Siguiendo con la serie de repasos de artículos técnicos clásicos, hoy toca hablar de "Monads for functional programming", el famoso paper de Philip Wadler publicado en 1995. Es uno de esos textos que, aunque tiene ya varias décadas, sigue siendo una referencia obligada para entender de dónde viene el concepto de mónada tal como lo usamos hoy en lenguajes como Haskell, y cómo se ha filtrado (con distintos grados de fidelidad) a lenguajes más mainstream como JavaScript, Scala o Kotlin.

## El problema que resuelve

El punto de partida del artículo de Wadler es simple: la programación funcional pura, sin efectos secundarios, es elegante y fácil de razonar, pero en la práctica necesitamos lidiar con cosas como errores, estado mutable, entrada/salida o no determinismo. La pregunta que se hace Wadler es: ¿cómo incorporamos estas nociones "impuras" a un lenguaje funcional puro, sin sacrificar sus propiedades matemáticas?

Su respuesta es la mónada: una estructura que permite "envolver" valores junto con un contexto computacional, y componer esas computaciones de forma segura y predecible.

## La estructura básica

Wadler define una mónada a partir de dos operaciones fundamentales:

- **unit** (a veces llamada `return` o `pure`): toma un valor normal y lo "envuelve" en el contexto monádico.
- **bind** (el famoso operador `>>=` en Haskell): toma un valor envuelto y una función que produce otro valor envuelto, y los combina en uno solo, encargándose de "desempacar" y "empacar" automáticamente.

En pseudocódigo, algo como:

```
unit :: a -> M a
bind :: M a -> (a -> M b) -> M b
```

Lo interesante es que esta misma estructura abstracta sirve para modelar cosas muy distintas: el manejo de errores (mónada `Maybe`/`Option`), el estado (mónada `State`), la entrada/salida (mónada `IO`), el no determinismo (mónada de listas), entre otras.

## El ejemplo del intérprete

Una de las partes más didácticas del paper es cómo Wadler construye, paso a paso, un intérprete simple para un lenguaje de expresiones aritméticas, y muestra cómo distintas variantes del mismo intérprete (una con manejo de errores, otra con un contador de pasos de ejecución, otra con logging) se pueden escribir con prácticamente el mismo código, simplemente cambiando la mónada subyacente.

Esto ilustra el verdadero poder de la abstracción: en lugar de reescribir el intérprete cada vez que necesitamos añadir una nueva "capacidad" (manejo de errores, logging, estado), basta con cambiar la mónada que usamos, y buena parte de la lógica se mantiene intacta.

## ¿Por qué "Maybe" es el ejemplo favorito?

La mónada `Maybe` (o `Option` en otros lenguajes) suele ser el primer ejemplo que se enseña, porque es la más intuitiva: representa un valor que puede estar presente (`Just x` / `Some x`) o ausente (`Nothing` / `None`). El `bind` de esta mónada se encarga de propagar automáticamente el caso "ausente" sin que tengamos que escribir un `if` en cada paso:

```haskell
buscarUsuario :: Int -> Maybe Usuario
buscarEmail :: Usuario -> Maybe String

obtenerEmail :: Int -> Maybe String
obtenerEmail id = buscarUsuario id >>= buscarEmail
```

Si `buscarUsuario` devuelve `Nothing`, la cadena entera se detiene y devuelve `Nothing`, sin que tengamos que comprobar manualmente en cada paso si el valor anterior existía. Esto debería sonar familiar a quien haya usado `Optional` en Java, `Option` en Scala/Kotlin, o incluso el operador de encadenamiento opcional (`?.`) en JavaScript, que resuelve un problema muy similar de forma más limitada.

## Relación con la programación imperativa

Otro punto que destaca el paper es cómo las mónadas permiten "domesticar" el estado mutable y otros efectos dentro de un lenguaje puro, sin romper la transparencia referencial. La mónada `State`, por ejemplo, permite escribir código que parece imperativo (encadenando operaciones que modifican un estado) pero que, por debajo, sigue siendo completamente funcional: en realidad se está pasando el estado de forma explícita entre cada operación, solo que la sintaxis de `bind` oculta ese detalle.

## ¿Por qué sigue siendo relevante hoy?

Aunque el paper está escrito pensando en Haskell (que por entonces todavía era un lenguaje relativamente joven), sus ideas se han filtrado a prácticamente todo el ecosistema de lenguajes con soporte funcional. Los `Promise` de JavaScript, por ejemplo, tienen una estructura muy similar a una mónada (aunque no cumplen todas las leyes matemáticas formales): `.then()` se comporta de forma parecida a `bind`, encadenando computaciones asíncronas sin que tengamos que lidiar manualmente con callbacks anidados.

De forma similar, los `Stream` de Java, los `Observable` de RxJS, o los `Result`/`Either` que se usan para manejo de errores en Rust, Kotlin o Scala, son todos primos cercanos de las mónadas descritas por Wadler.

## Conclusión

"Monads for functional programming" no es una lectura sencilla si no se tiene algo de familiaridad previa con Haskell y notación matemática, pero el esfuerzo vale la pena: entender de dónde viene el concepto de mónada ayuda muchísimo a reconocer el mismo patrón cuando aparece disfrazado en otros lenguajes, ya sea como `Optional`, `Promise`, `Either` o `Result`. Si trabajas habitualmente con alguno de estos tipos y quieres entender la teoría que hay detrás, este paper —aunque tenga ya treinta años— sigue siendo una de las mejores puertas de entrada.
