# Sobrevivir en Swift: Parte 1

Llegas a Swift desde JavaScript, Python, Java o Kotlin. Abres Xcode, escribes cuatro líneas que en tu lenguaje de siempre funcionarían sin problema y el compilador te devuelve un muro de errores rojos. Bienvenido. No es personal: Swift es un lenguaje que **prefiere quejarse al compilar antes que dejarte fallar en producción**.

Esta serie no pretende ser una referencia exhaustiva (para eso está [The Swift Programming Language](https://docs.swift.org/swift-book/)). Es un kit de supervivencia: lo mínimo que necesitas entender para dejar de pelearte con el compilador y empezar a escribir código que funcione. En esta primera parte veremos cinco conceptos que, si los entiendes bien desde el principio, te ahorrarán horas de frustración:

1. `let` frente a `var`
2. Opcionales
3. `struct` frente a `class`
4. Enums de verdad
5. Manejo de errores

Vamos allá.

---

## 1. `let` primero, `var` solo si hace falta

En Swift declaras constantes con `let` y variables con `var`:

```swift
let nombre = "Ada"
var contador = 0

contador += 1      // ✅
nombre = "Grace"   // ❌ Cannot assign to value: 'nombre' is a 'let' constant
```

La regla de supervivencia es simple: **usa `let` por defecto**. Si más adelante necesitas cambiar el valor, el compilador te avisará y lo cambias a `var`. De hecho, si declaras algo con `var` y nunca lo modificas, Xcode te mostrará un aviso sugiriendo que uses `let`.

¿Por qué tanta insistencia? Porque el código donde las cosas no cambian es más fácil de razonar, y en cuanto entremos en concurrencia (Parte 3, spoiler) agradecerás no tener estado mutable flotando por ahí.

Fíjate también en que no hemos escrito ningún tipo. Swift infiere que `nombre` es un `String` y `contador` un `Int`. Puedes ser explícito si quieres:

```swift
let precio: Double = 9.99
```

Pero una vez que el tipo está decidido, no cambia. Swift es estáticamente tipado: un `Int` no se convierte mágicamente en `String`, ni un `Int` en `Double` sin que tú lo pidas:

```swift
let unidades = 3
let total = precio * unidades          // ❌ Binary operator '*' cannot be applied...
let total = precio * Double(unidades)  // ✅
```

Al principio esto molesta. Con el tiempo te darás cuenta de cuántos bugs sutiles te está evitando.

## 2. Opcionales: el concepto que más te va a doler (y más te va a salvar)

Este es el gran choque cultural. En Swift, **una variable normal nunca puede ser `nil`**. Si un valor puede faltar, tienes que decirlo explícitamente con un tipo opcional, marcado con `?`:

```swift
var apodo: String? = nil   // puede ser un String... o nada
var nombre: String = nil   // ❌ 'nil' cannot initialize specified type 'String'
```

`String?` no es un `String`. Es una caja que puede contener un `String` o estar vacía. Y no puedes usar lo que hay dentro sin abrir la caja primero:

```swift
let apodo: String? = "Lovelace"
print(apodo.count)   // ❌ Value of optional type 'String?' must be unwrapped
```

Hay varias formas de abrirla. Estas son las que usarás el 95 % del tiempo.

### `if let`: abrir si hay algo

```swift
if let apodo {
    print("Hola, \(apodo). Tiene \(apodo.count) letras.")
} else {
    print("Sin apodo")
}
```

Dentro del bloque, `apodo` ya es un `String` normal. (La sintaxis abreviada `if let apodo` existe desde Swift 5.7; en código antiguo verás `if let apodo = apodo`, que es lo mismo.)

### `guard let`: salir pronto si no hay nada

```swift
func saludar(_ apodo: String?) {
    guard let apodo else {
        print("No sé cómo llamarte")
        return
    }
    print("Hola, \(apodo)")
}
```

`guard` es el patrón de "salida temprana": compruebas las precondiciones al principio y el resto de la función trabaja con valores ya desenvueltos, sin pirámides de `if` anidados. Si un `guard` no sale de su ámbito (con `return`, `throw`, `break`...), el compilador se queja. Es una red de seguridad.

### `??`: un valor por defecto

```swift
let mostrar = apodo ?? "Anónimo"
```

Corto y claro. Si `apodo` es `nil`, se usa `"Anónimo"`.

### Encadenamiento opcional con `?.`

```swift
let longitud = apodo?.count   // longitud es Int?
```

Si `apodo` es `nil`, toda la expresión es `nil` en lugar de explotar.

### `!`: el botón de autodestrucción

```swift
let longitud = apodo!.count
```

El signo de exclamación significa "confía en mí, aquí hay un valor". Si te equivocas, la app se cierra en ese mismo instante. Hay casos legítimos para usarlo, pero como regla de supervivencia: **cada `!` que escribas es una apuesta**. Si no puedes explicar en una frase por qué es imposible que sea `nil`, usa `guard let` o `??`.

## 3. `struct` frente a `class`: valores y referencias

En muchos lenguajes, todo lo que no es un primitivo es un objeto que se pasa por referencia. En Swift no. Tienes dos herramientas principales para crear tus propios tipos, y se comportan de forma muy distinta.

Un `struct` es un **tipo de valor**: cuando lo asignas o lo pasas a una función, se copia.

```swift
struct Punto {
    var x: Int
    var y: Int
}

var a = Punto(x: 0, y: 0)
var b = a
b.x = 10

print(a.x)  // 0
print(b.x)  // 10
```

Una `class` es un **tipo de referencia**: las dos variables apuntan al mismo objeto.

```swift
class Contador {
    var valor = 0
}

let c1 = Contador()
let c2 = c1
c2.valor = 10

print(c1.valor)  // 10 😱
```

Fíjate en un detalle curioso: `c1` y `c2` son `let`, y aun así hemos cambiado `valor`. Eso es porque `let` en una clase protege la *referencia* (no puedes hacer que `c1` apunte a otro objeto), pero no el contenido. En un `struct`, en cambio, `let` congela todo:

```swift
let p = Punto(x: 1, y: 1)
p.x = 5   // ❌ Cannot assign to property: 'p' is a 'let' constant
```

Otra sorpresa: si un método de un `struct` modifica sus propiedades, tienes que marcarlo como `mutating`:

```swift
struct Punto {
    var x: Int
    var y: Int

    mutating func mover(dx: Int, dy: Int) {
        x += dx
        y += dy
    }
}
```

**¿Cuál uso?** La recomendación oficial de Apple es empezar con `struct` y pasar a `class` cuando necesites identidad compartida (varios sitios que deben ver y modificar el mismo objeto), herencia, o interoperar con APIs de Objective-C que lo exijan. `String`, `Array`, `Dictionary` e `Int` son todos `struct`, así que ya estás usando tipos de valor constantemente sin saberlo.

## 4. Enums que sí sirven para algo

Si vienes de lenguajes donde un enum es una lista glorificada de constantes numéricas, prepárate. En Swift los enums son ciudadanos de primera clase.

```swift
enum EstadoPedido {
    case pendiente
    case enviado(numeroSeguimiento: String)
    case entregado(fecha: Date)
    case cancelado(motivo: String?)
}
```

Cada caso puede llevar **valores asociados** de tipos distintos. Y el `switch` te obliga a cubrirlos todos:

```swift
func describir(_ estado: EstadoPedido) -> String {
    switch estado {
    case .pendiente:
        return "Preparando tu pedido"
    case .enviado(let numero):
        return "En camino. Seguimiento: \(numero)"
    case .entregado(let fecha):
        return "Entregado el \(fecha.formatted(date: .abbreviated, time: .omitted))"
    case .cancelado(let motivo):
        return "Cancelado: \(motivo ?? "sin motivo")"
    }
}
```

Si mañana añades un caso `.devuelto`, el compilador marcará en rojo cada `switch` que no lo contemple. No hay que buscar a mano, no hay que acordarse. Es una de las mejores herramientas para modelar estados de forma que **los estados imposibles no se puedan ni escribir**.

Por cierto, los opcionales que vimos antes son exactamente esto: un enum con dos casos, `.none` y `.some(valor)`. Swift simplemente le pone azúcar sintáctico encima.

## 5. Errores: `throws`, `try` y nada de excepciones silenciosas

Swift no tiene excepciones al estilo Java en el sentido de que no pueden aparecer "por sorpresa". Si una función puede fallar, lo declara con `throws`, y quien la llama está obligado a reconocerlo con `try`.

Primero defines tus errores, normalmente con un enum:

```swift
enum ErrorRetiro: Error {
    case saldoInsuficiente(faltan: Double)
    case cuentaBloqueada
}
```

Luego la función que puede fallar:

```swift
func retirar(_ cantidad: Double, de saldo: Double) throws -> Double {
    guard cantidad <= saldo else {
        throw ErrorRetiro.saldoInsuficiente(faltan: cantidad - saldo)
    }
    return saldo - cantidad
}
```

Y para llamarla tienes tres opciones.

**`do / catch`** cuando quieres manejar el error:

```swift
do {
    let nuevoSaldo = try retirar(150, de: 100)
    print("Nuevo saldo: \(nuevoSaldo)")
} catch ErrorRetiro.saldoInsuficiente(let faltan) {
    print("Te faltan \(faltan) €")
} catch {
    print("Error inesperado: \(error)")
}
```

**`try?`** cuando solo te importa si funcionó o no; el resultado se convierte en opcional:

```swift
let saldo = try? retirar(50, de: 100)   // Double?
```

**`try!`** cuando estás absolutamente seguro de que no fallará. Mismo aviso que con `!`: si te equivocas, la app se cae.

Lo importante es que **la palabra `try` marca visualmente cada punto donde algo puede salir mal**. Al leer código ajeno sabes exactamente dónde mirar.

## Resumen para sobrevivir

- Usa `let` por defecto; `var` solo cuando el compilador te lo pida.
- `nil` solo existe en tipos opcionales (`?`). Ábrelos con `if let`, `guard let` o `??`. Desconfía de cada `!`.
- `struct` se copia, `class` se comparte. Empieza por `struct`.
- Los enums con valores asociados y `switch` exhaustivo son tu mejor arma para modelar estados.
- Las funciones que fallan se marcan con `throws` y se llaman con `try`. Nada se rompe en silencio.

Si te quedas con una sola idea, que sea esta: **el compilador de Swift no es tu enemigo, es tu primer revisor de código**. Cada error que te muestra es un bug que no llegará a tus usuarios.

Y en la Parte 3 nos meteremos con `async/await`, actores y la concurrencia estricta de Swift 6, que es donde de verdad se pone a prueba la supervivencia.
