# Certificación de dominio con Let’s Encrypt, NGINX y Docker Compose

Publicar una aplicación es emocionante hasta que el navegador muestra “No es seguro”. Para habilitar HTTPS necesitamos un certificado TLS, configurar el servidor y asegurarnos de renovarlo antes de que expire.

En este tutorial conectaremos tres piezas: **Let’s Encrypt** emitirá el certificado, **Certbot** gestionará su solicitud y **NGINX** atenderá las conexiones. Docker Compose organizará los contenedores y los directorios compartidos.

El resultado será un sitio accesible mediante HTTPS, con redirección desde HTTP y renovación automatizada.

Antes de empezar, una precisión: este certificado acredita el control del dominio y permite autenticar la conexión. No certifica la identidad comercial ni la confiabilidad del contenido.

### Prepara el dominio y el servidor

Necesitas un servidor Linux con Docker Engine y el complemento Docker Compose instalados. Los comandos siguientes utilizan Bash.

También debes tener:

- Un dominio cuyo registro `A` apunte a la IP pública del servidor.
- Un registro `AAAA` correcto si publicas IPv6.
- Los puertos TCP 80 y 443 abiertos.
- Acceso al servidor para crear archivos y programar tareas.

Usaremos `ejemplo.com`; reemplázalo por tu dominio en todos los archivos.

La validación será **HTTP-01**: Certbot escribirá un archivo temporal y Let’s Encrypt intentará recuperarlo mediante el puerto 80. Este método no permite certificados wildcard. Puedes consultar los detalles en la [documentación de desafíos](https://letsencrypt.org/docs/challenge-types/).

### Organiza los archivos

Crea esta estructura:

```bash
mkdir -p nginx/conf.d certbot/www certbot/conf html
echo '<h1>HTTPS funcionando</h1>' > html/index.html
```

Los directorios de Certbot conservarán tanto los archivos de validación como los certificados. Mantenerlos fuera del contenedor permite recrearlo sin perder ese estado.

Crea `compose.yaml`:

```yaml
services:
  nginx:
    image: nginx:stable-alpine
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - ./html:/usr/share/nginx/html:ro
      - ./certbot/www:/var/www/certbot:ro
      - ./certbot/conf:/etc/letsencrypt:ro

  certbot:
    image: certbot/certbot:latest
    volumes:
      - ./certbot/www:/var/www/certbot
      - ./certbot/conf:/etc/letsencrypt
```

Certbot tendrá permisos de escritura; NGINX solamente necesitará leer los archivos. Para un despliegue reproducible, fija las imágenes a versiones o digests que hayas validado.

### Arranca primero con HTTP

Hay un detalle fundamental: NGINX no puede cargar certificados que todavía no existen. Por eso comenzaremos con una configuración exclusivamente HTTP.

Guarda lo siguiente en `nginx/conf.d/default.conf`:

```nginx
server {
    listen 80;
    server_name ejemplo.com;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        root /usr/share/nginx/html;
        index index.html;
    }
}
```

Levanta el servidor:

```bash
docker compose up -d nginx
```

Antes de solicitar el certificado, comprueba la ruta compartida:

```bash
mkdir -p certbot/www/.well-known/acme-challenge
echo 'ok' > certbot/www/.well-known/acme-challenge/prueba
curl http://ejemplo.com/.well-known/acme-challenge/prueba
```

Haz esta comprobación desde una conexión externa cuando sea posible. Debes recibir `ok`. Si falla, revisa DNS, firewall y cualquier proxy intermedio antes de continuar.

### Solicita el certificado

Ejecuta Certbot con el método `webroot`:

```bash
docker compose run --rm certbot certonly \
  --webroot \
  --webroot-path=/var/www/certbot \
  --cert-name ejemplo.com \
  --email admin@ejemplo.com \
  --agree-tos \
  --non-interactive \
  -d ejemplo.com
```

Sustituye también el correo por una dirección que controles.

`certonly` obtiene el certificado sin modificar NGINX. `--cert-name` establece un nombre predecible para sus rutas. El funcionamiento de estas opciones está descrito en la [guía oficial de Certbot](https://eff-certbot.readthedocs.io/en/stable/using.html).

Si necesitas cubrir `www.ejemplo.com`, configura primero su DNS y añade otro argumento `-d www.ejemplo.com`. Todos los nombres solicitados deben superar la validación.

### Activa HTTPS

Reemplaza el contenido de `default.conf` por:

```nginx
server {
    listen 80;
    server_name ejemplo.com;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        return 301 https://ejemplo.com$request_uri;
    }
}

server {
    listen 443 ssl;
    server_name ejemplo.com;

    ssl_certificate
        /etc/letsencrypt/live/ejemplo.com/fullchain.pem;
    ssl_certificate_key
        /etc/letsencrypt/live/ejemplo.com/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;

    location / {
        root /usr/share/nginx/html;
        index index.html;
    }
}
```

`fullchain.pem` contiene el certificado y los intermediarios necesarios; `privkey.pem` contiene la clave privada. NGINX utiliza ambos para establecer HTTPS, como explica su [documentación de configuración TLS](https://nginx.org/en/docs/http/configuring_https_servers.html).

Conservamos la ruta del desafío en HTTP para futuras renovaciones. Las demás solicitudes se redirigen al dominio configurado.

Valida y recarga:

```bash
docker compose exec -T nginx nginx -t
docker compose exec -T nginx nginx -s reload
```

Abre `https://ejemplo.com` y verifica que el navegador acepte el certificado.

### Automatiza la renovación

Emitir el certificado es solamente una parte del trabajo. También necesitas comprobar periódicamente si corresponde renovarlo y hacer que NGINX cargue los archivos actualizados.

Primero realiza una simulación:

```bash
docker compose run --rm certbot renew --dry-run
```

Después configura una tarea en el cron del servidor con permisos para ejecutar Docker. Este ejemplo se ejecuta dos veces al día:

```cron
17 3,15 * * * cd /opt/mi-sitio && docker compose run --rm certbot renew --quiet && docker compose exec -T nginx nginx -t && docker compose exec -T nginx nginx -s reload
```

Cambia `/opt/mi-sitio` por la ruta absoluta del proyecto. La recarga también ocurrirá cuando no haya certificados pendientes; es una simplificación deliberada. Configura registros y alertas para detectar fallos de la tarea.

### Resuelve los problemas más comunes

Si la validación falla, comprueba que el dominio resuelva al servidor correcto y que ningún registro IPv6 dirija el tráfico a otra máquina.

Si NGINX no inicia, revisa las rutas y confirma que la emisión terminó correctamente. Monta todo `/etc/letsencrypt`, porque sus archivos incluyen enlaces hacia otros directorios.

Por último, protege `certbot/conf`: contiene claves privadas. Exclúyelo del repositorio y conserva respaldos con acceso restringido. Con la emisión, la recarga y la renovación resueltas, tu despliegue tendrá una base práctica para servir tráfico mediante HTTPS.
