# ¿Componentes de clase o funcionales?

Si llevas un tiempo en React, seguramente te has cruzado con código que usa `class App extends React.Component` y con otro que usa `function App()`. Durante años fue una decisión importante. Hoy la respuesta corta es casi siempre la misma: **componentes funcionales**. Aun así, vale la pena entender por qué, y cuándo la clase todavía tiene sentido.

## Cómo era el mundo de las clases

Antes de React 16.8, los componentes funcionales eran "tontos": recibían props y devolvían JSX, sin estado propio ni acceso al ciclo de vida. Si necesitabas estado o efectos secundarios, tenías que usar una clase.

```jsx
class Contador extends React.Component {
  constructor(props) {
    super(props);
    this.state = { cuenta: 0 };
    this.incrementar = this.incrementar.bind(this);
  }

  componentDidMount() {
    document.title = `Cuenta: ${this.state.cuenta}`;
  }

  componentDidUpdate() {
    document.title = `Cuenta: ${this.state.cuenta}`;
  }

  incrementar() {
    this.setState(prev => ({ cuenta: prev.cuenta + 1 }));
  }

  render() {
    return <button onClick={this.incrementar}>{this.state.cuenta}</button>;
  }
}
```

Funciona, pero hay bastante ceremonia: el constructor, el `bind` del método, y la lógica del título repetida entre `componentDidMount` y `componentDidUpdate`.

## La misma idea con hooks

```jsx
function Contador() {
  const [cuenta, setCuenta] = useState(0);

  useEffect(() => {
    document.title = `Cuenta: ${cuenta}`;
  }, [cuenta]);

  return <button onClick={() => setCuenta(c => c + 1)}>{cuenta}</button>;
}
```

El código es más corto, y la lógica relacionada está junta. En la versión de clase, el efecto estaba partido entre dos métodos de ciclo de vida. Con `useEffect`, la dependencia `[cuenta]` deja claro cuándo debe ejecutarse.

## Ventajas de los funcionales

**1. Menos código y menos sorpresas.** No hay `this`, así que desaparecen los problemas de binding y de contexto que tanta gente tropezaba al pasar callbacks.

**2. Lógica reutilizable con hooks.** Antes se usaban HOC o *render props*, que añadían capas al árbol de componentes. Un hook personalizado comparte lógica sin tocar la jerarquía:

```jsx
function useWindowWidth() {
  const [ancho, setAncho] = useState(window.innerWidth);

  useEffect(() => {
    const onResize = () => setAncho(window.innerWidth);
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);

  return ancho;
}
```

**3. Mejor encaje con las herramientas modernas.** El equipo de React recomienda hooks en la documentación nueva, las optimizaciones del compilador y los modos concurrentes están pensados para funciones, y la mayoría de librerías del ecosistema ya expone API basadas en hooks.

**4. Menos duplicación de lógica.** Con `componentDidMount` y `componentDidUpdate` era fácil olvidar uno de los dos. Con `useEffect` la intención queda en un solo lugar.

## Lo que todavía no cubren los hooks

Hay un caso concreto en el que las clases siguen siendo necesarias: los **Error Boundaries**. Hoy por hoy, `componentDidCatch` y `getDerivedStateFromError` solo existen en componentes de clase. Puedes usar librerías como `react-error-boundary` que envuelven esta lógica en un componente funcional, pero por debajo sigue habiendo una clase.

Fuera de eso, las clases son una opción válida si tu base de código ya está escrita así y migrarla no aporta nada. React mantiene compatibilidad con ellas y no hay planes de eliminarlas.

## Mi recomendación

- **Código nuevo:** componentes funcionales con hooks, sin dudarlo.
- **Código existente:** migra cuando toques el componente por otra razón, no solo por estética. Reescribir clases que funcionan bien suele dar más riesgo que beneficio.
- **Error Boundaries:** usa una clase o una librería que la encapsule.

La pregunta de "clase o funcional" ya no es un debate técnico abierto. Es más bien una cuestión de qué tan rápido quieres escribir código que el resto del ecosistema entiende sin esfuerzo. Y en 2026, eso son funciones con hooks.
