# Certificación de dominio con Let’s Encrypt, NGINX y Docker Compose

Publicar una aplicación sin HTTPS ya no es una opción razonable. Además de proteger credenciales y datos en tránsito, un certificado TLS evita advertencias del navegador y mejora la confianza de quienes visitan el sitio.

En este tutorial configuraremos un dominio con HTTPS usando **NGINX**, **Let’s Encrypt**, **Certbot** y **Docker Compose**. La aplicación podrá ser cualquier servicio HTTP disponible como contenedor.

## Requisitos

Necesitas:

- Un servidor con Docker y Docker Compose.
- Un dominio apuntando a la IP pública del servidor.
- Los puertos `80` y `443` abiertos.
- Acceso al servidor mediante SSH.

Antes de continuar, confirma que los registros DNS del dominio resuelven correctamente:

```bash
dig +short ejemplo.com
dig +short www.ejemplo.com
```

Ambos deberían mostrar la IP pública de tu servidor. La propagación DNS puede tardar desde unos minutos hasta varias horas.

## Estructura del proyecto

Crearemos la siguiente estructura:

```text
mi-proyecto/
├── compose.yaml
├── nginx/
│   └── conf.d/
│       └── default.conf
└── certbot/
    ├── conf/
    └── www/
```

Los certificados se almacenarán en `certbot/conf`, mientras que `certbot/www` contendrá los archivos temporales utilizados para validar el dominio.

Puedes crear los directorios con:

```bash
mkdir -p nginx/conf.d certbot/conf certbot/www
```

## Configuración inicial de NGINX

Let’s Encrypt debe verificar que controlamos el dominio. Utilizaremos el desafío HTTP-01: Certbot colocará un archivo especial bajo la ruta `/.well-known/acme-challenge/` y Let’s Encrypt intentará descargarlo mediante HTTP.

Crea `nginx/conf.d/default.conf`:

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name ejemplo.com www.ejemplo.com;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        proxy_pass http://app:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Sustituye los dominios y el puerto de la aplicación según tu caso. El nombre `app` será resuelto por la red interna de Docker Compose.

## Docker Compose

Ahora crea `compose.yaml`:

```yaml
services:
  app:
    image: mi-aplicacion:latest
    restart: unless-stopped
    expose:
      - "3000"

  nginx:
    image: nginx:alpine
    restart: unless-stopped
    depends_on:
      - app
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - ./certbot/www:/var/www/certbot:ro
      - ./certbot/conf:/etc/letsencrypt:ro

  certbot:
    image: certbot/certbot:latest
    volumes:
      - ./certbot/www:/var/www/certbot
      - ./certbot/conf:/etc/letsencrypt
```

En este ejemplo, la aplicación no publica su puerto directamente en el servidor. Solo NGINX puede acceder a ella dentro de la red creada por Compose. Esto reduce la superficie expuesta.

Inicia la aplicación y NGINX:

```bash
docker compose up -d app nginx
```

Comprueba que la versión HTTP sea accesible:

```bash
curl -I http://ejemplo.com
```

## Obtener el certificado

Ejecuta Certbot mediante un contenedor temporal:

```bash
docker compose run --rm certbot certonly \
  --webroot \
  --webroot-path /var/www/certbot \
  --email correo@ejemplo.com \
  --agree-tos \
  --no-eff-email \
  -d ejemplo.com \
  -d www.ejemplo.com
```

Certbot escribirá el desafío en el volumen compartido. NGINX lo servirá por el puerto 80 y Let’s Encrypt validará el dominio. Si el proceso termina correctamente, los certificados aparecerán en:

```text
certbot/conf/live/ejemplo.com/
```

Los archivos más importantes son:

- `fullchain.pem`: certificado y cadena intermedia.
- `privkey.pem`: clave privada del certificado.

La clave privada no debe publicarse ni añadirse al repositorio.

## Activar HTTPS

Modifica `nginx/conf.d/default.conf` para redirigir HTTP a HTTPS y utilizar el certificado:

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name ejemplo.com www.ejemplo.com;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;

    server_name ejemplo.com www.ejemplo.com;

    ssl_certificate /etc/letsencrypt/live/ejemplo.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ejemplo.com/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_timeout 1d;
    ssl_session_cache shared:SSL:10m;

    location / {
        proxy_pass http://app:3000;
        proxy_http_version 1.1;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Valida la configuración:

```bash
docker compose exec nginx nginx -t
```

Si la prueba es satisfactoria, recarga NGINX:

```bash
docker compose exec nginx nginx -s reload
```

Ahora visita:

```text
https://ejemplo.com
```

También puedes inspeccionar la respuesta desde la terminal:

```bash
curl -I https://ejemplo.com
```

## Renovación automática

Los certificados de Let’s Encrypt tienen una vigencia limitada, por lo que debemos renovarlos periódicamente. Certbot solo reemplaza un certificado cuando está próximo a vencer; ejecutar el comando con frecuencia es seguro.

Una solución sencilla consiste en añadir una tarea al `cron` del servidor:

```cron
0 3 * * * cd /ruta/absoluta/mi-proyecto && docker compose run --rm certbot renew --webroot --webroot-path /var/www/certbot && docker compose exec nginx nginx -s reload
```

La tarea se ejecutará diariamente a las 03:00. Si Certbot renueva algún certificado, NGINX se recargará para comenzar a utilizarlo.

Antes de confiar en la automatización, simula una renovación:

```bash
docker compose run --rm certbot renew --dry-run
```

El modo `--dry-run` utiliza el entorno de pruebas de Let’s Encrypt y permite detectar errores sin consumir los límites del servicio de producción.

## Errores frecuentes

Si la validación falla, revisa estos puntos:

- El dominio debe resolver a la IP correcta.
- El puerto 80 debe ser accesible desde Internet.
- Un firewall o proveedor de nube podría estar bloqueando el tráfico.
- La ruta `/.well-known/acme-challenge/` no debe redirigirse durante la validación.
- NGINX y Certbot deben compartir exactamente el mismo volumen para `/var/www/certbot`.
- Si utilizas un proxy externo o CDN, su configuración puede interferir con el desafío.

También conviene consultar los registros:

```bash
docker compose logs nginx
```

Y verificar manualmente la ruta de validación creando un archivo temporal dentro de `certbot/www/.well-known/acme-challenge/`.

## Conclusión

Con esta arquitectura, cada componente tiene una responsabilidad clara: la aplicación atiende peticiones internas, NGINX funciona como proxy inverso y termina la conexión TLS, Certbot administra los certificados y Docker Compose coordina los servicios.

El resultado es una configuración reproducible, sencilla de desplegar y capaz de renovar automáticamente sus certificados. A partir de aquí puedes incorporar encabezados de seguridad, compresión, límites de peticiones, monitoreo y copias de respaldo del directorio de Let’s Encrypt para preparar el sistema para producción.
