Llegas a Swift desde JavaScript, Python, Java o Kotlin y, durante las primeras horas, todo parece familiar. Hay llaves, hay funciones, hay clases. Luego el compilador empieza a decirte que no. Que no puedes usar ese valor porque "podría ser nil". Que no puedes modificar esa propiedad porque `self` es inmutable. Que tu `switch` no es exhaustivo.

Esta serie es la guía que me habría gustado tener entonces. No es un tutorial completo del lenguaje: es un mapa de los sitios donde casi todo el mundo tropieza y de las ideas que hay detrás. En esta primera parte vemos los cuatro pilares que más cambian tu forma de escribir código: `let` frente a `var`, los opcionales, los tipos por valor y los enums.

## 1. `let` por defecto, `var` cuando haga falta

En Swift declaras constantes con `let` y variables con `var`:

```swift
let nombre = "Ada"
var intentos = 0

intentos += 1      // bien
nombre = "Grace"   // error: 'nombre' es una constante
```

La regla de supervivencia es simple: **escribe siempre `let` y cambia a `var` solo cuando el compilador te lo pida**. De hecho, si declaras un `var` que nunca modificas, el propio compilador te avisa.

No es una cuestión estética. Cuando lees una función de cuarenta líneas y casi todo es `let`, sabes que esos valores no cambian por el camino, y puedes concentrarte en los dos o tres `var` que sí lo hacen.

Un detalle que sorprende: los tipos se infieren, pero son estrictos. No hay conversiones implícitas entre números:

```swift
let entero = 3
let decimal = 2.5
let suma = Double(entero) + decimal   // la conversión es explícita
```

Molesta el primer día y te ahorra errores sutiles el resto del año.

## 2. Opcionales: el `nil` que no puedes ignorar

Este es el gran filtro. En la mayoría de lenguajes, cualquier referencia puede ser nula y te enteras en ejecución. En Swift, un `String` **siempre** contiene una cadena. Si puede faltar, el tipo es otro: `String?`.

```swift
let edadTexto = "42"
let edad = Int(edadTexto)   // el tipo es Int?, no Int
```

`Int("42")` puede fallar (¿y si el texto fuera `"hola"`?), así que devuelve un opcional. Y un opcional no se puede usar directamente: hay que desenvolverlo. Tienes varias herramientas, y conviene saber cuándo usar cada una.

### `if let`: cuando solo te interesa el caso con valor

```swift
if let edad = Int(edadTexto) {
    print("Tienes \(edad) años")
} else {
    print("Eso no es un número")
}
```

Desde Swift 5.7, si la variable ya existe puedes usar la forma abreviada:

```swift
func saludar(nombre: String?) {
    if let nombre {
        print("Hola, \(nombre)")
    }
}
```

### `guard let`: para salir pronto

`guard` es la herramienta que más limpia el código. Comprueba una condición y, si no se cumple, te obliga a abandonar el ámbito. Lo desenvuelto queda disponible en el resto de la función:

```swift
func procesar(pedido: Pedido?) {
    guard let pedido else {
        print("No hay pedido")
        return
    }

    // Aquí 'pedido' ya no es opcional
    print("Procesando \(pedido.id)")
}
```

Compáralo con anidar tres `if let` uno dentro de otro. Con `guard`, las comprobaciones quedan arriba y el camino feliz sigue sin sangrado extra.

### `??`: un valor por defecto

```swift
let apodo: String? = nil
let visible = apodo ?? "Anónimo"
```

### `?.`: encadenamiento opcional

```swift
let numeroDeLetras = usuario?.direccion?.calle.count
```

Si cualquier eslabón es `nil`, la expresión completa vale `nil`. El resultado es, por tanto, un opcional (`Int?` en este caso).

### `!`: el botón rojo

```swift
let edad = Int(edadTexto)!   // si es nil, la app se cierra
```

El desenvoltorio forzado le dice al compilador "confía en mí". Si te equivocas, el programa termina en el acto. Tiene usos legítimos (recursos que sabes que existen, tests), pero cada `!` que escribas para que el compilador se calle es un cierre inesperado esperando su momento. Si no puedes explicar en una frase por qué ese valor nunca será `nil`, usa `guard let`.

## 3. `struct` frente a `class`: copias frente a referencias

Si vienes de Java o de C#, tu instinto es modelarlo todo con clases. En Swift ocurre lo contrario: la opción por defecto es `struct`. `String`, `Array`, `Dictionary` e `Int` son structs en la biblioteca estándar.

La diferencia fundamental es que **los structs se copian y las clases se comparten**:

```swift
struct PuntoValor {
    var x: Int
}

final class PuntoReferencia {
    var x: Int
    init(x: Int) { self.x = x }
}

var a = PuntoValor(x: 1)
var b = a
b.x = 99
print(a.x)   // 1: 'b' es una copia independiente

let c = PuntoReferencia(x: 1)
let d = c
d.x = 99
print(c.x)   // 99: 'c' y 'd' apuntan al mismo objeto
```

Fíjate en dos cosas del ejemplo.

Primera: `c` y `d` están declarados con `let` y aun así modificamos `x`. Con una clase, `let` congela la referencia, no el contenido. Con un struct, `let` lo congela todo: un `let a = PuntoValor(x: 1)` no admite cambios en `a.x`, aunque la propiedad sea `var`.

Segunda: el struct no necesitó `init`. Swift genera un inicializador con todas sus propiedades.

Esto explica también un error clásico:

```swift
struct Contador {
    var total = 0

    mutating func incrementar() {
        total += 1
    }
}
```

Sin la palabra `mutating`, el compilador protesta: los métodos de un struct no pueden modificar sus propiedades salvo que lo declares. Es una señal explícita de qué métodos cambian el valor.

¿Y no es lento copiar un array de un millón de elementos? No, porque las colecciones estándar usan *copy-on-write*: la copia real solo ocurre si alguien modifica una de las dos.

¿Cuándo usar una clase, entonces?

- Cuando necesitas **identidad**: dos partes del programa deben ver el mismo objeto y sus cambios.
- Cuando necesitas herencia o trabajas con APIs que la exigen (gran parte de UIKit, por ejemplo).
- Cuando gestionas un recurso con ciclo de vida propio, como una conexión o un archivo.

Para todo lo demás (modelos de datos, configuraciones, estados), usa `struct`. Te ahorra una categoría entera de errores, la de "¿quién ha cambiado este objeto?".

## 4. Enums: mucho más que una lista de constantes

En muchos lenguajes un enum es un número con nombre. En Swift, cada caso puede llevar datos asociados, y eso lo convierte en una herramienta de modelado de primer nivel:

```swift
enum EstadoDeCarga {
    case inactivo
    case cargando(progreso: Double)
    case completado(datos: [String])
    case fallido(mensaje: String)
}
```

Piensa en la alternativa habitual: un `isLoading: Bool`, un `data` opcional y un `error` opcional. Son tres propiedades que permiten combinaciones absurdas, como estar cargando, con datos y con error a la vez. Con el enum, **los estados imposibles no se pueden representar**.

Para consumirlo usas `switch`, que en Swift debe ser exhaustivo:

```swift
func describir(_ estado: EstadoDeCarga) -> String {
    switch estado {
    case .inactivo:
        return "Esperando"
    case .cargando(let progreso):
        return "Cargando: \(Int(progreso * 100)) %"
    case .completado(let datos):
        return "Hay \(datos.count) elementos"
    case .fallido(let mensaje):
        return "Error: \(mensaje)"
    }
}
```

Dos detalles importantes. No hay `break`: cada caso termina solo, sin caída accidental al siguiente. Y si mañana añades un caso `.cancelado`, el compilador te marcará todos los `switch` que no lo contemplan. Por eso conviene evitar `default` en los enums propios: con él, el compilador deja de avisarte.

Y aquí se cierra el círculo con el punto 2: un opcional es, literalmente, un enum de la biblioteca estándar con dos casos, `.none` y `.some(valor)`. Toda la sintaxis de `?`, `if let` y `??` es azúcar sobre esa idea.

## Kit de supervivencia

Si solo te quedas con cinco cosas de este post:

1. **`let` por defecto.** Usa `var` solo cuando sea necesario.
2. **Un opcional es un tipo distinto.** Desenvuélvelo con `if let`, `guard let` o `??`.
3. **Cada `!` es una apuesta.** Asegúrate de poder justificarla.
4. **`struct` por defecto.** Deja `class` para cuando necesites identidad compartida.
5. **Modela estados con enums** y deja que el `switch` exhaustivo trabaje para ti.

El patrón común es que Swift traslada los errores del momento de ejecución al momento de compilación. Al principio parece que el compilador te lleva la contraria. Con el tiempo descubres que cada queja es un fallo que no llegará a tus usuarios.
